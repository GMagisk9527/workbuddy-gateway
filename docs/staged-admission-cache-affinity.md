# 分阶段准入与缓存亲和

## 前处理和长流分开限制

将以下字段合入现有配置：

```json
{
  "admission": {"maxActive":8,"maxPreparing":2,"maxWaiting":8,"waitTimeoutMs":15000},
  "scheduling": {"affinityWaitMs":250,"cacheAffinityWaitMs":1500,"waitTimeoutMs":15000}
}
```

`maxActive` 仍是整个 HTTP 请求至结算结束的硬数量上限。`maxPreparing` 是其内部额外的读入/解码/转换上限；
三协议完成转换并进入公共上游入口时归还前处理名额，账号等待、模型生成和 SSE 不再占用它。
取消、拒绝和 panic 都归还名额；总请求名额、账号并发、输入/输出内存预算仍覆盖原有生命周期。
这里不提前释放仍可能被请求、转换或重试引用的输入字节。

新生成配置为 8 个总请求、2 个前处理。旧配置省略或设 `maxPreparing:0` 保留旧行为；
`maxActive` 省略仍为 2，不会因升级扩容。开启阶段控制时 `maxPreparing` 必须不超过 `maxActive`。
总准入与前处理各有有界 FIFO，前处理等待者已计入总在途上限；两次获取共享总等待期限，避免排队时间翻倍。
缩容不中断已有请求；禁用阶段控制会唤醒原前处理队列。新值可热加载。

性能接口 runtime 增加 `preparingActive`、`preparingLimit`、`preparingWaiting`；
原 `admissionActive` 继续包含长流与尚在等待前处理的请求，不能把二者相加。

## 有证据才延长缓存亲和

`cacheAffinityWaitMs:0` 保留旧策略；新生成配置为 1500 毫秒，允许最大 10000。
只有当前转换后的请求至少 256KiB、同一调用方/模型的绑定账号近期有至少两次完整成功响应，
且上游每次明确报告至少 32768 个缓存读取 token，才使用较长亲和等待。
普通本地亲和命中不构成缓存证据，缺少 usage、失败和不完整响应不能补充证据。
证据五分钟过期，明确零/少量缓存命中或账号绑定变化立即清除；依附原有有界 LRU，不新增无上限状态。
总调度等待期限始终优先；免费站点优先、账号名单、冷却、额度和硬并发规则保持原样。

该策略利用已观测的缓存结果，不能证明上游缓存一定按账号隔离，也不保证更长等待一定更快。
应结合自己的模型验证收益；关闭新字段即可恢复固定软亲和等待，无需改消息正文或请求身份。
